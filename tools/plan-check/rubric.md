# Rubric: is this plan ready to post and build from?

Grade the substance of the proposed change, not its length, headings, or polish. Explicitly scoped-down work can be ready; hidden omissions cannot. Planned tests need not have been run yet. Do not require automated tests universally.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | Candidate plan's stated cause compared with Issue, Repro evidence (including controls), and relevant Thread highlights; evidence guide: Diagnosis and grounding. | The proposed cause explains the reproduced failure and is consistent with the supplied controls and established facts. An unproven mechanism may be a clearly stated hypothesis with a concrete confirmation step; it must not contradict the reproduction or be presented as already proved. | required |
| bounded-scope | Candidate plan's included/excluded work and all proposed changes, read against Issue and its diagnosis; evidence guide: Scope. | The changes serve one bounded fix or explicitly bounded part of it. The package identifies what it will change and what it leaves alone; explicit exclusions may appear anywhere. Every proposed change fits that boundary, rather than adding unrelated cleanup, features, or a broad rewrite. Deferring part of an issue is allowed when stated honestly. | required |
| executable | Candidate plan's implementation locations, approach, ordering, and unresolved decisions; evidence guide: Executability. | The plan identifies concrete files, functions, or code areas and the behavior to change, with enough direction for a stranger to begin. It resolves execution-blocking choices or gives a specific investigation/decision step before dependent implementation. Exact line numbers and a named file for a purely manual test are not required. | required |
| test-decisive | Candidate plan's test steps and expected results compared with the failure and controls in Repro evidence; evidence guide: Test plan. | A repeatable manual or automated check would distinguish the original failure from the intended success for the declared scope. It names the triggering steps or refers unambiguously to the supplied reproduction, and states an observable expected-after result. A general suite run or unrelated symptom test alone does not pass. Relevant controls remain checkable. | required |
| honest-claims | Candidate plan's assertions, risks, unknowns, exclusions, and deviations; Candidate plan comment; compare with supplied observations and maintainer cautions; evidence guide: Honesty. | Plans, observations, and uncertainties are distinguished. No unsupported completed-result claim, contradicted certainty, hidden scope reduction, or material ignored known risk makes the package misleading. Ordinary proposed mechanisms do not need exhaustive proof or a separate Risks heading when no specific blocker is shown. | required |
| comment-faithful | Candidate plan comment compared with the actual plan, Issue, Repro evidence, and substantive Thread highlights; evidence guide: Comms. | The comment describes this issue's own diagnosis and bounded work accurately, without claiming an unbuilt change has already succeeded, piggybacking someone else's plan, or ignoring an explicit maintainer direction that applies to the proposed work. A terse accurate comment can pass. | required |
| stated-conventions | Repo facts' actual contribution/AI-use policies and Thread highlights' explicit asks compared with Candidate plan and comment; evidence guide: Comms. | The proposal and comment meet stated requirements relevant to this stage, such as required AI-use disclosure, human-written comment requirements, or required coordination before implementation. Do not invent an AI policy, demand unrelated bug-report-template fields in a plan comment, or treat limited review bandwidth as a total ban. Lack of stated requirements is not a failure. | required |

## Verdict rule

Return `accept` (ready) only when every required check is `pass`. Any required `fail` or `unclear` returns `reject` (hold). Preferred checks, if added later, never change the verdict. Grade every check even after finding a blocker. `unclear` is a check grade, never a third verdict.
